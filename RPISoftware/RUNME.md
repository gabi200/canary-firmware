# RUNME — Canary hub

How to run Canary. **Section 1** deploys the hub on a Raspberry Pi and connects the
real ESP32 sensors. **Section 2** covers the laptop development flows. **Section 3**
spreads the hub over three Raspberry Pis that cover for each other (one may fail).
Overview and known limitations: [`README.md`](./README.md). Troubleshooting: [`DEBUG.md`](./DEBUG.md).
The MQTT/API contract between the firmware and the hub is
[`docs/HARDWARE.md`](./docs/HARDWARE.md).

```
ESP32 air / water ──MQTT :1883──▶ Mosquitto ──▶ backend (FastAPI, SQLite) ──▶ nginx :80  ──▶ web dashboard (raw + analysis)
                                                          └─────── :8000 (REST + WS) ─────▶ mobile app (analysis only)
```

```
backend/     FastAPI: MQTT ingestion, detection, incidents, analysis, REST + WebSocket
web/         React dashboard; in Docker it is served by nginx, which also proxies the API
mobile/      Flutter resident app
mosquitto/   broker config (its password file is generated by scripts/pi_setup.sh)
simulator/   hw_sim.py (firmware-accurate air + water nodes), building_sim.py (many rooms), simulate.py (legacy)
scripts/     pi_setup.sh (secrets + MQTT users), smoke.sh, mobile_check.sh
cluster/     three-Pi mode (section 3): Patroni and keepalived images, hailo-ollama unit for the AI HAT+ 2
```

## 1. Raspberry Pi hub

`docker compose up -d` runs three containers that restart on their own after a reboot:

| Service | Port | What |
|---|---|---|
| `mosquitto` | 1883 | MQTT broker; every client logs in (no anonymous access) |
| `backend` | 8000 | FastAPI + MQTT consumer; SQLite on the `canary_backend_data` volume |
| `web` | 80 | dashboard; proxies `/api` (incl. WebSocket), `/health`, `/docs` to the backend |

### 1.1 What you need

- Raspberry Pi 4 or 5 (2 GB RAM or more) with **64-bit** Raspberry Pi OS (Bookworm or
  newer), on the same LAN or IoT VLAN as the sensors. Check: `uname -m` prints `aarch64`.
- No reserved address needed: the hub announces itself as **`canary-hub.local`** (the
  `announcer` service, mDNS), which sensors use as their MQTT host and the app finds by itself.
  The Pi's `avahi-daemon` must run (it does by default on Raspberry Pi OS).
- The sensors flashed with the firmware in `../air_sensor` / `../water_sensor`.

### 1.2 Install Docker (once)

```bash
curl -fsSL https://get.docker.com | sh       # Docker Engine + the compose plugin
sudo usermod -aG docker "$USER"              # use docker without sudo...
# ...then log out and back in (or reboot), and check:
docker run --rm hello-world
docker compose version                       # Docker Compose version v2.24 or newer
```
(Prefer apt? Follow Docker's "Install Docker Engine on Debian" guide instead. Debian's
own `docker-compose` package is too old for this compose file.)

### 1.3 Get the code

```bash
sudo apt-get install -y git
git clone <this-repository-url> canary-firmware
cd canary-firmware/RPISoftware
```

### 1.4 Create the secrets and the sensors' MQTT users

Pick one name per sensor. It becomes the sensor's MQTT user **and** its MQTT base
topic (the hub names the node after it), so make it unique and descriptive:

```bash
scripts/pi_setup.sh air-kitchen water-kitchen
```

This creates `.env` (mode 600, gitignored) with a random `CANARY_JWT_SECRET`,
`CANARY_MQTT_PASSWORD` (the backend's broker user `hub`), `CANARY_CARE_KEY` (encrypts care
profiles; keep it, a lost key makes them unreadable) and `CANARY_ESCALATION_SECRET` (signs the
escalation webhook; give it to the ARC / 112 partner). It also writes the broker's
password file `mosquitto/config/passwd` (owned by the broker's uid 1883, mode 600,
gitignored) and prints, for each new sensor, the values to type into its portal:

```
-- Sensor 'air-kitchen': enter in its setup portal ------------------------------
   MQTT enabled (0 or 1)               : 1
   MQTT host                           : canary-hub.local
   MQTT port                           : 1883
   MQTT user                           : air-kitchen
   MQTT password (leave blank to keep) : 3f1c9a...        <- shown only now: store it
   MQTT base topic                     : air-kitchen   (unique per device)
```

Safe to re-run at any time. Existing secrets and sensor passwords are kept. Add a sensor
later with `scripts/pi_setup.sh water-bath`. A lost password is replaced with
`scripts/pi_setup.sh --rotate air-kitchen`, after which you re-enter it in the portal.
If the printed host is wrong (several network interfaces), re-run with
`CANARY_HUB_HOST=<pi-lan-ip> scripts/pi_setup.sh ...`.

### 1.5 Start the hub

```bash
docker compose up -d --build        # first build on a Pi takes a few minutes
docker compose ps                   # mosquitto, backend, web: "Up ... (healthy)"
curl -s localhost/health            # {"status":"ok","service":"canary-backend",...}
```

It starts again by itself after a reboot (`restart: unless-stopped`). To update, install the
updater once (section 1.11) and use **Administration → Hub → Software**, or by hand:
`git pull && docker compose up -d --build`.

### 1.6 Connect each ESP32

For every sensor, open its setup portal (Wi-Fi `canary-setup` for the air sensor,
`water-sensor-setup` for the water sensor, on first boot; afterwards hold the config
button while the device boots). The details are under "Provisioning, configuration,
and recovery" in [`../air_sensor/README.md`](../air_sensor/README.md) and
[`../water_sensor/README.md`](../water_sensor/README.md). Enter your Wi-Fi and the
values `pi_setup.sh` printed: **MQTT enabled `1`**, MQTT host = the Pi's IP, port
`1883`, user, password, and the **unique** base topic. After you save, the device
restarts and connects.

### 1.7 Verify the sensors

Watch the broker. The safer way keeps the password out of every command line: it is
piped from `.env` into a root-only options file inside the broker container.

```bash
printf -- '-u hub\n-P %s\n' "$(sed -n 's/^CANARY_MQTT_PASSWORD=//p' .env)" |
  docker compose exec -T mosquitto sh -c 'umask 077 && cat > /tmp/hub.opts'
docker compose exec mosquitto mosquitto_sub -o /tmp/hub.opts -v -t '#'
```

The quick way works too, but `-P <password>` on a command line can be read by any
local process (`ps`) while it runs:

```bash
docker compose exec mosquitto mosquitto_sub -u hub -P "$(sed -n 's/^CANARY_MQTT_PASSWORD=//p' .env)" -v -t '#'
```

Expected: retained messages arrive right away, then a status on every change and every
heartbeat (air 15 s, water 60 s):
```
air-kitchen/availability online
air-kitchen/status {"device":{"name":"canary","firmware":"1.0.0"},"uptime_ms":61234,...}
water-kitchen/availability online
water-kitchen/status {"device":{"name":"water-sensor","firmware":"1.0.0"},"uptime_ms":...}
```

Then open the dashboard at **`http://<pi-ip>/`** and sign in as `mihai` (manager). The
**Sensors** page (`/sensors`) shows every device's raw status and the hub's analysis.
New sensors land in the seeded demo building `bld_007`, zone `zone_hallway`, and wait under
**New sensors** on **Administration → Devices** (sign in as `tehnician`, `mihai` or `admin`):
press **Beep** to find an air sensor, then choose its room (or select a room on
**Administration → Rooms** and press **Put in this room**). Or through the API (any
`admin`/`mihai`/`tehnician` token; zone ids are listed by `GET /api/v1/buildings/bld_007/zones`):

```bash
HUB=http://<pi-ip>
TOKEN=$(curl -s $HUB/api/v1/auth/token -H 'content-type: application/json' \
  -d '{"username":"admin"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
curl -s -X PATCH $HUB/api/v1/nodes/air-kitchen -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d '{"zone_id":"zone_kitchen","name":"Kitchen air"}'
```

Mobile app (analysis only; see [`mobile/README.md`](./mobile/README.md)). On the same
Wi-Fi it finds the hub by itself (`_canary-hub._tcp`, announced by the `announcer`
service); no address is built in:
```bash
flutter build apk --release
flutter run --dart-define=CANARY_API=http://<pi-ip>:8000     # development: try this address first
```

### 1.8 Test without hardware

`hw_sim.py` plays one air and one water sensor exactly like the firmware: same topics,
retained status and availability, last will `offline`, heartbeats, and status documents
with the firmware's own state rules. It logs in as `hub`, so it needs no extra setup:

```bash
docker compose --profile sim run --rm hw-sim --scenario co --fast
```

| `--scenario` | What the hub sees |
|---|---|
| `normal` (default) | steady state with small drifts; runs until Ctrl-C |
| `co` / `gas` / `smoke` | CO ppm / MQ5 ADC / PM2.5+PM10 ramp through warning into danger (alarm sounding) and back |
| `leak` | water wet → alarm sounding, valve closed, `leak_latched`; then dry but still latched |
| `presence` | radar presence toggles: empty / moving / stationary |
| `offline` | the air node drops off (the broker publishes its will `offline`), then reconnects |
| `reboot` | both nodes restart: `uptime_ms` resets, air warm-up starts again |
| `all` | `co`, `gas`, `smoke`, `leak` (then an `OPEN` command clears the latch), `presence`, `offline`, `reboot` in sequence |

`--fast` runs all firmware timers, heartbeats and the scenario 5x faster. The defaults
are base topics `canary` and `water-sensor`, the firmware defaults. Use `--air-base` /
`--water-base` to keep the simulated nodes apart from real sensors. A 20 s air warm-up is
simulated (`--warmup 300` is the firmware default). After a scenario the nodes stay online
until Ctrl-C (`--exit` stops right away). Stopping drops the connections, so the hub marks
them offline, just like unplugging a device. Commands work like the firmware, e.g. clearing
the leak latch after `--scenario leak`:

```bash
docker compose exec mosquitto mosquitto_pub -o /tmp/hub.opts -t water-sensor/valve/set -m OPEN
```

Firmware pushes from **Administration → Firmware** work against the simulator too:
`--ota-port 8081` serves the firmware's `/api/ota` (air on 8081, water on 8082) and adds
`wifi.ip` to the status documents. A push with the right token reboots the node into the
next patch version (1.1.0 → 1.1.1); a wrong token is refused like on the device:

```bash
docker compose --profile sim run --rm hw-sim --ota-port 8081 --ota-bind 0.0.0.0
```

In the dashboard, open **Device access** on each node: the address is the reported IP plus
the port (e.g. `172.18.0.7:8081`, water `:8082`), the token `sim-device-token` (`--ota-token` /
`OTA_TOKEN`). Any ESP32-S3 / ESP32-C3 application `.bin` passes the hub's image check.

The legacy `canary.telemetry.v1` simulator (the seeded demo building's sensors) still runs:
`docker compose --profile sim run --rm simulator --scenario gas_leak`.

#### Simulare pe mai multe camere (many rooms at once)

`building_sim.py` pornește, într-un singur proces, câte un nod de aer și/sau de apă (identic cu
`hw_sim.py`) pentru fiecare cameră din `simulator/rooms.demo.json`: 14 camere și 21 de noduri.
Fiecare apartament (Ap. 12, 13, 14) are aceleași camere: Bucătărie (aer + apă), Baie (aer + apă),
Living (aer), Dormitor (aer). Spațiile comune: Hol scară (aer), Centrală termică (aer + apă). Camerele care lipsesc din hub sunt create prin API-ul de admin (la
a doua pornire le regăsește după nume, nu le dublează), apoi fiecare nod e mutat în camera lui, cu
un nume ca „Bucătărie · aer". Butoanele de test hardware din dashboard și din aplicație (TEST,
SILENCE, OPEN/CLOSE) merg și pe nodurile simulate. Simulatorul vorbește doar cu brokerul și cu
API-ul hubului (`HUB_URL`), cu nimic din afară.
*EN: one process plays every room of the config, creates the missing zones and puts each node in its room.*

**Oprește întâi `hw-sim`** (și containere ca `sim-kitchen`): folosesc aceleași topicuri
(`air-kitchen`, `water-kitchen`...), deci camerele s-ar dubla. `building-sim` refuză să pornească
dacă un topic de-al lui e deja online (`--force` sare peste verificare).
*EN: stop the single-pair sims (hw-sim) first, or the rooms get duplicate nodes.*

```bash
docker compose --profile sim run --rm building-sim        # pornește, interactiv; Ctrl-C oprește   (EN: start, interactive)
docker compose --profile sim up -d building-sim           # sau în fundal                         (EN: or in the background)
docker compose --profile sim attach building-sim          # tastezi comenzi; Ctrl-P Ctrl-Q iese    (EN: type commands; detach)
docker compose --profile sim stop building-sim            # oprește: nodurile trec offline         (EN: stop, nodes go offline)
docker compose --profile sim run --rm building-sim --config rooms.small.json --fast   # 3 camere   (EN: 3 rooms, 5x faster)
```

| Tastezi (EN: type) | Ce face (EN: what happens) |
|---|---|
| `bucatarie 12 gaz` | bucătăria din Ap. 12 primește scenariul gaz (EN: `kitchen gas`) |
| `baie 13 scurgere` | scurgere în baia din Ap. 13: alarmă, valva se închide (EN: `bath_13 leak`) |
| `baie 12 deschide` | OPEN pe valvă, șterge blocarea după scurgere (EN: `bath_12 open`); și `inchide`, `test`, `liniste` |
| `toate normal` | toate camerele revin la normal (EN: `all normal`) |
| `list` / `help` / `quit` | camere și stări / ajutor / oprire |

Camera se scrie ca id de zonă (`kitchen`, `bath_12`) sau ca nume plus apartament (`bucatarie 12`,
`baie ap 13`; `hol`, `centrala` n-au nevoie), fără diacritice, mari sau mici. Scenarii: `normal`, `gaz`, `co`, `fum`, `scurgere`, `prezenta`,
`offline`, `repornire`, `toate` (merg și numele englezești din tabelul de mai sus). Un scenariu
terminat revine singur la `normal`. La pornire: `--scenario kitchen=gas` (de repetat),
`--only kitchen,bath_12`, `--fast`, `--warmup 300`, `--duration 600`. Fără Docker (vezi 2.3):
`python building_sim.py --config rooms.small.json`. Pentru alte camere copiază `rooms.demo.json`
(`kind`: kitchen, living_room, bedroom, bathroom, hallway, stairwell, boiler, other; `pos` în metri).
Camerele create rămân în hub. Le ștergi cu `DELETE /api/v1/admin/zones/{id}`, după ce le-ai mutat
nodurile (de ex. în `zone_hallway`).

**Escalation webhook (ARC / 112 partner) without a partner.** `arc-sim` stands in for the
partner: it checks the HMAC signature and the ±5 min timestamp exactly like a real receiver
must, prints each event, and answers 200. It uses the same `CANARY_ESCALATION_SECRET` from
`.env` (re-run `scripts/pi_setup.sh` once if your `.env` predates it). Point the backend at it
and restart the backend:

```bash
echo 'CANARY_ESCALATION_URL=http://arc-sim:8099/canary' >> .env
docker compose --profile sim up -d arc-sim
docker compose up -d backend          # picks up the new .env value
docker compose logs -f arc-sim        # then trigger an incident, e.g. hw-sim --scenario co
```

An escalation, evacuation or resolution then shows up in the `arc-sim` log, and the dashboard
lists the deliveries (`GET /api/v1/incidents/{id}/escalations`). To watch retries, start it as
`docker compose --profile sim run --rm --service-ports arc-sim --fail-first 2`. Remove
`CANARY_ESCALATION_URL` from `.env` to switch the webhook off again (notification rows only).

### 1.9 Operations

| Task | Command |
|---|---|
| Logs | `docker compose logs -f backend mosquitto` (dashboard requests: `docker compose logs web`) |
| Stop / start | `docker compose down` / `docker compose up -d` (data stays in the volumes) |
| Wipe all data | `docker compose down -v` (database **and** retained MQTT messages) |
| Back up the database | `docker compose stop backend && docker compose cp backend:/data ./canary-backup-$(date +%F) && docker compose start backend` (copies `canary.db` with its WAL files) |
| Port 80 already taken (e.g. Pi-hole) | add `CANARY_HTTP_PORT=8080` to `.env`, `docker compose up -d` → `http://<pi-ip>:8080/` |
| Other backend settings | add any `CANARY_*` from docs/HARDWARE.md section 6 to `.env` (except the MQTT connection, which `docker-compose.yml` fixes), then `docker compose up -d` |
| Raw history retention | hourly, the backend deletes raw status documents, readings and occupancy older than `CANARY_RETENTION_DAYS` (default 14; `0` keeps everything). Incidents, their events, check-ins and the audit log are never deleted |
| Postgres instead of SQLite | set `CANARY_DATABASE_URL=postgresql+asyncpg://canary:<password>@<host>:5432/canary` in `.env` (you run that Postgres; SQLite is plenty for one building). Timescale hypertables are created only if that server has the extension. There are no migrations: a database created by an earlier version of the hub needs `ALTER TABLE sensor_readings ALTER COLUMN seq TYPE bigint;` once (`seq` holds the device uptime in ms). Redis is not used |
| New `hub` password | delete the `CANARY_MQTT_PASSWORD` line from `.env`, `scripts/pi_setup.sh`, then `docker compose up -d` |
| Remove a sensor's login | `docker run --rm --network none --entrypoint mosquitto_passwd -v "$PWD/mosquitto/config:/mosquitto/config" eclipse-mosquitto:2 -D /mosquitto/config/passwd air-kitchen` (ignore the "owner is not root" warning), then `docker compose kill -s SIGHUP mosquitto` |

### 1.10 Security notes

- **Trusted network only.** The firmware speaks plaintext MQTT and HTTP (no TLS), and so
  does the hub: broker passwords, commands and status cross the network in clear text.
  Keep the Pi and the sensors on a trusted LAN or an isolated IoT VLAN, and never forward
  ports 1883, 8000 or 80 from the internet. Docker-published ports bypass `ufw` rules, so
  restrict access at the router/VLAN.
- **Dashboard login is username-only** (dev tokens: `mihai`, `dispecer`, `tehnician`, `admin`, `ana`).
  This is a known MVP limitation: anyone who can reach port 80/8000 can sign in. The
  dev HTTP ingress `POST /api/v1/telemetry` needs no token at all, so anyone who can
  reach the hub can also inject readings.
- **Tokens stay out of the logs.** The dashboard and the app pass their JWT to the
  WebSocket as `?token=`: uvicorn logs it as `token=***`. For that location nginx's access
  log leaves out the query string and its error log records only `crit` messages.
- **One MQTT user per sensor**, so a lost or retired device can be revoked alone.
  `allow_anonymous false` is enforced.
- **Secrets stay local.** `.env` and `mosquitto/config/passwd` are gitignored: never commit
  them. Avoid passwords in command arguments (`-P`, `--password`): other local processes
  can read them. Prefer the options file above and the `MQTT_PASSWORD` environment variable
  for the simulators.
- Use `canary-hub.local` as the sensors' MQTT host: it follows the Pi's address when DHCP or the
  hotspot changes it.

### Optional: per-device ACLs

By default every authenticated client may use every topic. You can pin each sensor to
its own base topic. This works only when **every sensor's MQTT user equals its base
topic** (the naming `pi_setup.sh` suggests). Otherwise the broker still accepts that
sensor's connection but **silently drops its publishes**, which is why this is not on by
default.

1. Create `mosquitto/config/acl`:
   ```
   # The backend (and the simulators, which log in as hub) may use every topic.
   user hub
   topic readwrite #

   # Every other user may only use <its username>/#, i.e. its own base topic.
   pattern readwrite %u/#
   ```
2. Add `acl_file /mosquitto/config/acl` to `mosquitto/config/mosquitto.conf`.
3. Hand the file to the broker's user and restart it:
   ```bash
   docker run --rm --network none --entrypoint sh -v "$PWD/mosquitto/config:/mosquitto/config" \
     eclipse-mosquitto:2 -c 'chown 1883:1883 /mosquitto/config/acl && chmod 600 /mosquitto/config/acl'
   docker compose restart mosquitto
   ```
4. Re-check section 1.7: every sensor must still show fresh `status` messages.

### 1.11 Updating the hub

Each Pi runs a small helper outside Docker, `canary-updater` (`cluster/updater`, Python standard
library only). The dashboard and `scripts/hub_update.sh` ask it to update; it does the `git` and
`docker compose` work, because the dashboard's own containers are rebuilt during an update.

**Install it once** (on every Pi of a three-Pi hub). `scripts/pi_setup.sh` writes the key
(`CANARY_UPDATER_KEY` in `.env`) and prints these lines with your user and path filled in:

```bash
sudo cp cluster/canary-updater.service /etc/systemd/system/
sudo sed -i "s|^User=.*|User=$USER|" /etc/systemd/system/canary-updater.service
sudo sed -i "s|^WorkingDirectory=.*|WorkingDirectory=$PWD/cluster|" /etc/systemd/system/canary-updater.service
sudo systemctl daemon-reload && sudo systemctl enable --now canary-updater
docker compose up -d     # the backend reads the new key from .env
```

It listens on port 8010 (the Pi's own address on three Pis) and answers only requests carrying
the key. Logs: `journalctl -u canary-updater`.

**From the dashboard:** **Administration → Hub** (admin, manager and technician accounts) shows
the newest commit on GitHub `main`, the commits not yet on every Pi, and on each Pi card the commit
it runs. The Pis check GitHub every 15 minutes; **Check now** checks at once.

- **Update all Pis** updates one Pi at a time. Each must be healthy on the new commit (its
  containers, `/health`, and on three Pis its Postgres member) before the next starts. The Pi
  holding the database leader goes last, and its leadership is handed to a replica before it
  restarts.
- **Update this Pi** updates only that Pi, for trying a change first.
- **Automatic rollback:** if the build fails, or the Pi is not healthy within 5 minutes, it goes
  back to the commit it ran before and says **rolled back** with the reason and the log. During
  "Update all" the rollout stops there; the Pis not reached keep their version. If the rollback
  fails too, the Pi shows **failed**: check it with `docker compose logs`.

An update is refused while a Pi is down or its updater does not answer, while another update
runs, or when a Pi's checkout has local changes, commits that are not on GitHub, or is not on
`main`. Every update is written to the audit log.

**From a shell** (on any Pi, same rules): `scripts/hub_update.sh status | fetch | all |
processing | web | ai | hub`.

**Check on real Pis** after installing or changing the updater:

1. One Pi: **Update this Pi** on a Pi that is behind: it ends **Up to date** on the new commit.
2. **Update all Pis** on three Pis: `docker compose exec postgres patronictl list` during the
   rollout shows the leader moving before its Pi restarts; the dashboard (VIP) stays usable apart
   from a short reconnect.
3. Push a commit that breaks the backend (e.g. a syntax error in `app/main.py`), **Update all
   Pis**: the first Pi rolls back, the rollout stops, the other two keep running. Revert the
   commit afterwards.

## 2. Laptop development

### 2.0 One-command smoke (no Docker, no Flutter)

Runs the backend tests, the web typecheck/build and static checks of the hub scripts,
simulators and compose file. Best first check.

```bash
bash scripts/smoke.sh                                    # ... SMOKE: PASS
cd backend && .venv/bin/python -m pytest -q              # backend only: 95 passed
```

### 2.1 The whole hub in Docker

Same as on the Pi (sections 1.4, 1.5, 1.8), on Docker Desktop or colima (arm64 or amd64).
On a laptop `pi_setup.sh` writes `CANARY_ANNOUNCE=0`, so the laptop never announces
`canary-hub.local` and cannot take sensors or phones away from a real hub on the same Wi-Fi:

```bash
scripts/pi_setup.sh            # .env + broker user "hub"
docker compose up -d --build   # dashboard http://localhost/ , API http://localhost:8000/docs
docker compose --profile sim run --rm hw-sim --scenario all --fast
```
On macOS, keep the checkout in a directory the Docker VM shares (Docker Desktop: `/Users`
by default; colima: your home directory). Otherwise the `mosquitto/config` bind mount is
empty and the broker cannot start.

### 2.2 Backend only — SQLite, no broker (fast)

```bash
cd backend
python3 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
export CANARY_DATABASE_URL="sqlite+aiosqlite:///./canary.db"
export CANARY_MQTT_ENABLED=false
export CANARY_JWT_SECRET="local-dev-secret-change-me-please-1234"
uvicorn app.main:app --reload --port 8000
# http://localhost:8000/docs ; schema + demo data auto-created on startup
```

Ingestion benchmark (40 simulated nodes through the real status handler on a throwaway SQLite
database; ms and SQL statements per status document, plus the polled REST endpoints):
`.venv/bin/python -m tools.bench_ingest` (add `--poll` to run the dashboard polling load alongside).
On a running hub, `GET /health` shows the MQTT backlog: `"ingest": {"queue": n, "lag_s": s}`.

To feed it MQTT, run only the broker in Docker (`scripts/pi_setup.sh` once, then
`docker compose up -d mosquitto`) and start the backend with:
```bash
export CANARY_MQTT_ENABLED=true CANARY_MQTT_HOST=localhost CANARY_MQTT_USERNAME=hub
export CANARY_MQTT_PASSWORD="$(sed -n 's/^CANARY_MQTT_PASSWORD=//p' ../.env)"
```

### 2.3 Drive sensors

**Firmware-accurate MQTT nodes** (needs a broker, e.g. `docker compose up -d mosquitto`):
```bash
cd simulator
python3 -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt
```

## 3. Three Raspberry Pis (redundant hub)

Three Pis run the same stack and cover for each other: any **one** of them may fail (power, disk,
cable) and the hub keeps detecting and alarming. Each Pi has a home role, which is also its name:

| Pi | Normally runs | If it fails, taken over by |
|---|---|---|
| `web` | the hub's floating IP (VIP): the sensors' MQTT broker, the dashboard, the app's API | `processing`, then `ai` |
| `processing` | MQTT ingestion, detection, incidents, notifications, retention | `web`, then `ai` |
| `ai` | triangulation, the signature shadow model, incident briefs (LLM on a Raspberry Pi AI HAT+ 2) | `processing`, then `web` (no HAT there: briefs use a template) |

Besides section 1's three containers, every Pi runs `etcd` (how the Pis agree on who leads),
`postgres` (PostgreSQL under Patroni: a primary, a synchronous standby and a replica, so a failover
never loses a saved write), `pgproxy` (HAProxy: sends the backend's database connections to
whichever Pi holds the primary) and `keepalived` (moves the VIP). The one-Pi hub (SQLite) stays
the default; nothing in this section changes it.

### 3.1 What you need

- **Three Raspberry Pi 5** (4 GB RAM or more; a Pi 4 works, slower) with 64-bit Raspberry Pi OS.
  The AI Pi needs **Raspberry Pi OS Trixie** for the AI HAT+ 2.
- **An SSD or NVMe drive per Pi, strongly recommended.** Postgres and etcd write all the time: an SD
  card wears out and stalls, and a stalled Pi looks like a dead one (needless failovers). Keep at
  least **8 GB free** per Pi: the images alone take about 1.5 GB, building them on the Pi more.
- **Wired Ethernet**, all three on the same LAN / VLAN as the sensors.
- **Four fixed addresses in a private `/24` the network (router or hotspot) does not hand out**:
  one per Pi plus the VIP. They are added to each Pi's Wi-Fi/Ethernet profile next to its DHCP
  address (step 2 prints the `nmcli` lines), so the cluster keeps working when the hotspot phone,
  and with it the DHCP subnet, changes. Example: VIP `10.91.13.240`, `processing` `.170`, `web`
  `.188`, `ai` `.241`. Sensors and the app never use these: they find the hub as
  `canary-hub.local`, at the hub Pi's DHCP address.
- Optional: a **Raspberry Pi AI HAT+ 2** on the AI Pi (section 3.4).
- No firewall between the Pis (Raspberry Pi OS has none by default). Otherwise open TCP 80, 1883,
  2379, 2380 (etcd), 5432 (Postgres), 8000 (backend), 8008 (Patroni), 8010 (canary-updater) and IP protocol 112 (VRRP).
- **The same time on all three.** Raspberry Pi OS sets its clock over the internet; on a LAN
  without internet, point `systemd-timesyncd` at a local NTP server (most routers have one: `NTP=`
  in `/etc/systemd/timesyncd.conf`). Incidents, events and device commands carry timestamps from
  different Pis. The backend log warns when a Pi is more than 2 s off, and `GET /api/v1/cluster`
  shows each Pi's offset (`clock_skew_s`).

### 3.2 Set up

1. On **all three** Pis: install Docker and get the code (sections 1.2 and 1.3).
2. On **one** Pi only, write the shared settings (sensor logins can be added here too, section 1.4):
   ```bash
   scripts/pi_setup.sh --cluster 10.91.13.240 10.91.13.170 10.91.13.188 10.91.13.241 air-kitchen
   #                             VIP          processing   web          ai
   ```
   Besides section 1.4's secrets it writes `CANARY_CLUSTER_MODE=triple`, `COMPOSE_PROFILES=cluster`
   (so `docker compose` also starts etcd, postgres, pgproxy and keepalived), the four addresses, the
   cluster and database passwords, the database URL (through `pgproxy`), the broker host (the VIP,
   for the processing Pi's backend) and the public URL (`canary-hub.local`). It also records which
   Pi it runs on (`CANARY_NODE_NAME`, `CANARY_NODE_IP`), and prints, per Pi, the `sudo nmcli`
   line that adds its fixed address: run each on its Pi before step 5.
3. Copy `.env` and `mosquitto/config/passwd` to the other two Pis. The script prints the commands:
   ```bash
   scp .env pi@192.168.1.12:canary-firmware/RPISoftware/.env
   sudo cat mosquitto/config/passwd | ssh pi@192.168.1.12 'umask 077; sudo tee canary-firmware/RPISoftware/mosquitto/config/passwd >/dev/null'
   ```
4. On each of the other two Pis: `scripts/pi_setup.sh` (no arguments). It finds the Pi's role from
   its address and hands the password file to the broker. "None of the three Pis' addresses" means
   the Pi did not get its reserved address: compare `hostname -I` with `.env`.
5. On **all three**, within a few minutes of each other: `docker compose up -d --build`.
6. Check, on any Pi:
   ```bash
   docker compose ps                              # + etcd, postgres, pgproxy, keepalived
   docker compose exec postgres patronictl list   # one Leader, one Sync Standby, one Replica
   curl -s http://canary-hub.local/health         # the hub Pi: "cluster": {"mode": "triple", ...}
   avahi-browse -rt _canary-hub._tcp              # exactly one "Canary hub", node=web normally
   ```
   The dashboard at **`http://canary-hub.local/`** (sign in as `admin`, `mihai` or `tehnician`) shows the Pis
   under **Administration → Hub** (`/admin/hub`): alive or not, what each runs, who holds the VIP.
7. Use **`canary-hub.local`** everywhere: as each sensor's **MQTT host** (the portal values
   `pi_setup.sh` prints already say so) and for the dashboard. The app finds the hub by itself.
   The name always points at the Pi holding the VIP, at its DHCP address, and moves with it.

### 3.3 Day to day

| Task | How |
|---|---|
| Add a sensor | on any one Pi `scripts/pi_setup.sh water-bath`, then copy `mosquitto/config/passwd` to the other two and run `scripts/pi_setup.sh` there (it reloads their brokers). Until then the new login works only on that Pi's broker |
| Simulators | `docker compose --profile sim run --rm hw-sim ...` from any Pi: they publish to the broker behind the VIP, like the sensors |
| Update | **Administration → Hub → Software** or `scripts/hub_update.sh all` (section 1.11; install the updater on all three Pis). By hand: one Pi at a time, `git pull && docker compose up -d --build`, then wait until `patronictl list` shows it `streaming` again |
| Logs | per Pi: `docker compose logs -f backend` (who processes, lease changes), `docker compose logs postgres pgproxy keepalived etcd` |
| Back up the database | on any Pi: `docker compose exec -T postgres pg_dump -U postgres canary > canary-$(date +%F).sql` |
| Change a cluster setting in `.env` | change it on all three Pis (copy the file), then `docker compose up -d` on each |

### 3.4 AI HAT+ 2 on the AI Pi

The `ai` Pi runs incident briefs on a Raspberry Pi AI HAT+ 2 (Hailo-10H) through Hailo's
`hailo-ollama` server. Without it the briefs come from a template; everything else is unaffected.

1. Raspberry Pi OS **Trixie** (64-bit). Install the HAT's driver and runtime, enable PCIe Gen 3, reboot:
   ```bash
   sudo apt update && sudo apt install -y dkms hailo-h10-all
   echo 'dtparam=pciex1_gen=3' | sudo tee -a /boot/firmware/config.txt
   sudo reboot
   ```
2. Install Hailo's **Model Zoo GenAI** package (a `.deb` from Hailo); it provides `hailo-ollama`.
   Check where it went: `command -v hailo-ollama`. If that is not `/usr/bin/hailo-ollama`, fix the
   `ExecStart=` line of `cluster/hailo-ollama.service` first.
3. Run it as a service on port 11434 (its default, 8000, is the backend's port):
   ```bash
   sudo cp cluster/hailo-ollama.service /etc/systemd/system/
   sudo sed -i "s/^User=.*/User=$USER/" /etc/systemd/system/hailo-ollama.service   # run it as you
   sudo systemctl daemon-reload && sudo systemctl enable --now hailo-ollama
   ```
4. Download the model and try it:
   ```bash
   curl -s localhost:11434/api/pull -d '{"model": "qwen2.5-instruct:1.5b", "stream": false}'
   curl -s localhost:11434/api/tags            # or: curl -s localhost:11434/hailo/v1/list
   curl -s localhost:11434/api/chat -d '{"model": "qwen2.5-instruct:1.5b", "stream": false,
     "messages": [{"role": "user", "content": "Say hello in five words."}]}'
   ```
   Other models it offers: `qwen2:1.5b`, `llama3.2:3b`, `deepseek_r1_distill_qwen:1.5b`,
   `qwen2.5-coder:1.5b`. To use one, pull it and set `CANARY_LLM_MODEL=<model>` in `.env` on all
   three Pis.

The AI Pi's backend reaches the server as `CANARY_LLM_URL=http://host.docker.internal:11434`
(`scripts/pi_setup.sh` writes it on the AI Pi only). When the AI Pi is down, the briefs come from the
template on another Pi. A brief can take up to about a minute while the LLM runs; the alarm path never
waits for it.

### 3.5 What fails over, and how fast

Measured in a rehearsal on three simulated Pis (etcd, Patroni, pgproxy and keepalived as
configured here):

| What fails | What happens | How long |
|---|---|---|
| The VIP holder (normally `web`), or its dashboard / broker stops answering | keepalived moves the VIP to `processing`, else `ai` | 3-5 s (power or cable loss ~4 s, failed health check ~5 s, clean shutdown under 1 s) |
| The `processing` Pi | `web` (else `ai`) takes the processing lease and subscribes to MQTT | 15 s measured (the lease); about 45 s when that Pi also held the Postgres primary (database failover, then a 10 s pause for the Pis to report in) |
| The Pi with the Postgres primary | Patroni promotes the synchronous standby; every pgproxy cuts the sessions to the old primary and sends new ones to the new primary | ~20-30 s after a power or cable loss (23-26 s measured), ~5 s after a clean shutdown. No saved write is lost. Processing pauses meanwhile (nothing can be saved) and resumes on its own |
| The Pi with the synchronous standby | writes wait until Patroni picks the other replica | ~5 s |
| Any of the above, for the sensors | a sensor whose broker vanished reconnects to the VIP on its next publish (air every 15 s, water every 60 s) | up to about a minute without hub-side detection; the sensors' own alarms keep working |

**Any one Pi may fail.** With **two** down, etcd has no majority: Postgres turns read-only and the
hub stops recording (no new incidents) until one of them is back; the sensors still alarm locally.
A Pi cut off from the other two (cable out) turns its own Postgres read-only within seconds, so
there is never a second primary.

A Pi that comes back rejoins by itself (its containers restart with Docker): its Postgres as a
replica (rewound with `pg_rewind` if it was the primary), the VIP returns to `web` about 30 s after
web's dashboard answers again, and the processing role returns to `processing` once that Pi has
been up 30 s. The Postgres primary stays wherever it is now: that is normal. When the VIP moves,
some sensors can show **offline** for up to a minute: the broker they left still holds their old
"offline" message, until each one's next status (air 15 s, water 60 s) shows it online again.

A sensor keeps its broker for as long as the connection lasts, so after a hotspot drop it may stay on
a Pi that no longer holds the VIP. The `relay` service (`cluster/relay`, on all three Pis, idle on the
VIP's) copies live messages from that Pi's broker to the VIP's and commands back, so the sensor still
reaches the hub. `docker compose logs relay` lists each topic it forwards. It deliberately is not a
Mosquitto bridge: a bridge replays old retained messages as live ones on every reconnect, which could
raise a false incident. After changing it, run `cluster/relay/e2e_relay.sh` on a Pi: real brokers in a
private network, safe beside a running hub.

### 3.6 Failover drill

1. Open `http://<VIP>/admin/hub` and, on one Pi, `docker compose exec postgres patronictl list`:
   note which Pi is the Postgres Leader and which holds the VIP.
2. Pull the power plug of one Pi (any). (`sudo poweroff` is a clean shutdown: the handover is faster
   than after a real failure.)
3. Watch `/admin/hub` (reload the page if it stops updating: you may have unplugged the Pi that
   served it): the Pi turns down within about 10 s and its roles move to the others.
4. On a remaining Pi, `docker compose exec postgres patronictl list` shows a Leader again within
   about 30 s. A first `ERROR ... Max retries exceeded` line about the dead Pi's etcd is expected.
5. Within a minute every sensor is online again in the dashboard. Optionally trigger a test from a
   remaining Pi: `docker compose --profile sim run --rm hw-sim --scenario smoke --fast --exit`.
6. Power the Pi back on. After a few minutes `patronictl list` shows three members again and
   `/admin/hub` shows every role back on its home Pi.

### 3.7 Back to one Pi

On every Pi, stop the stack, then on the Pi that stays, take the three-Pi lines out of `.env` and
start it again:

```bash
docker compose down                       # on all three (COMPOSE_PROFILES=cluster: the cluster services too)
sed -i -E '/^(CANARY_CLUSTER_MODE|COMPOSE_PROFILES|CANARY_NODE_NAME|CANARY_NODE_IP|CANARY_VIP|CANARY_(PROCESSING|WEB|AI)_IP|CANARY_DATABASE_URL|CANARY_MQTT_HOST|CANARY_PUBLIC_URL)=/d' .env
docker compose up -d                      # one-Pi hub, SQLite
```

The one-Pi hub uses its own SQLite database again: what was recorded in three-Pi mode stays in the
`canary_pg_data` volume, it is not copied over. Point the sensors' MQTT host and the app back at
this Pi's own address (the VIP no longer exists). The cluster passwords may stay in `.env`.
