# Canary 🐤

**Smart Building Safety & Hazard-Response Platform** for multi-unit residential buildings
(Romanian HOA / *asociații de proprietari* context).

Canary connects to an in-building IoT sensor network (combustible gas, CO, smoke /
particulates, water leak, and presence: radar on the real air sensor, Wi-Fi in the legacy
demo) and drives the safety-critical path:

> **detection → alert → evacuation → victim-accounting**

This directory is the **Raspberry Pi hub**: it receives MQTT from the real Canary
sensors (`../air_sensor` ESP32-S3, `../water_sensor` ESP32-C3), stores and analyses it,
and serves the web dashboard and the mobile app. It runs with one command
(`docker compose up -d`) on 64-bit Raspberry Pi OS, and simulators stand in for the
hardware when there is none. The architecture and delivery plan is
**[`ARCHITECTURE.md`](./ARCHITECTURE.md)**; its "As built" section says which parts of the
plan this hub implements. The firmware ↔ hub contract (MQTT topics, status documents,
analysis vocabulary, API) is **[`docs/HARDWARE.md`](./docs/HARDWARE.md)**. Checks and
troubleshooting: **[`DEBUG.md`](./DEBUG.md)**.

```
ESP32 air / water ──MQTT──▶ Mosquitto ──▶ backend (FastAPI)
  (per-device login)          (Pi)          ├─ raw status history + canonical readings
                                            ├─ detection → incidents → evacuation → accounting
                                            ├─ analysis per node / zone / building
                                            └─ REST + WebSocket
                            web dashboard ◀─┤  raw + analysis   (nginx, port 80)
                            mobile app    ◀─┘  analysis only    (port 80 or 8000)
```

## Quickstart: Raspberry Pi (or any Docker host)

Full walk-through, including installing Docker and provisioning the ESP32 portals, in
**[`RUNME.md`](./RUNME.md) section 1**.

```bash
cd RPISoftware
scripts/pi_setup.sh air-kitchen water-kitchen   # .env secrets + one MQTT user per sensor;
                                                # prints what to type into each sensor's portal
docker compose up -d --build                    # Mosquitto :1883, backend :8000, dashboard :80
open http://<pi-ip>/                            # sign in as mihai

# no hardware? firmware-accurate simulated sensors:
docker compose --profile sim run --rm hw-sim --scenario co --fast
#   scenarios: normal | co | gas | smoke | leak | presence | offline | reboot | all
```

Watch live incidents over WebSocket (get a token first):

```bash
TOKEN=$(curl -s localhost:8000/api/v1/auth/token -H 'content-type: application/json' \
  -d '{"username":"mihai"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')

# any WS client, e.g. websocat:
websocat "ws://localhost:8000/api/v1/ws/incidents?building_id=bld_007&token=$TOKEN"
```

## Quickstart (no Docker — SQLite + HTTP ingest)

```bash
cd backend
python3 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
export CANARY_DATABASE_URL="sqlite+aiosqlite:///./canary.db"
export CANARY_MQTT_ENABLED=false
uvicorn app.main:app --reload
# then POST telemetry to /api/v1/telemetry (same pipeline as MQTT) — see tests for payloads
```

## Key endpoints

| Method | Path | Role |
|---|---|---|
| POST | `/api/v1/auth/token` | public (dev) |
| GET | `/api/v1/buildings/{id}/summary` | any (analysis only: mobile + dashboard; residents get no occupancy) |
| GET | `/api/v1/buildings/{id}/nodes` | manager / dispatcher / admin (raw + analysis) |
| GET | `/api/v1/nodes/{node_id}/history?minutes=60&fields=a,b` | manager / dispatcher / admin |
| PATCH | `/api/v1/nodes/{node_id}` (`zone_id`, `name`) | manager / admin |
| GET | `/api/v1/buildings/{id}/incidents?active=true` | any |
| GET | `/api/v1/incidents/{id}/events` | any |
| GET | `/api/v1/incidents/{id}/accounting` | manager / dispatcher |
| POST | `/api/v1/incidents/{id}/checkin` | resident |
| POST | `/api/v1/incidents/{id}/dismiss` \| `/order-evacuation` \| `/resolve` | manager / dispatcher |
| POST | `/api/v1/telemetry` | dev ingress, no auth (prod = MQTT) |
| WS | `/api/v1/ws/incidents?building_id=&token=` | authenticated |

`system_admin` passes every role check. REST timestamps are UTC with a `Z` suffix.
Payload shapes of the hardware endpoints: [`docs/HARDWARE.md`](./docs/HARDWARE.md) sections 3–5.
The safety rules applied to hardware readings (device thresholds only when sane, a
device's own alarm never downgraded, only the reporting device can clear its incident,
smoke never auto-evacuates) are in its section 2.

## Web — Operations dashboard (React)

`web/` — role-based console (React + TS + Vite): **Manager/HOA** view (floor plan, live
sensor status, an Environment card for the hardware nodes, trends, device health, incident
actions), **Dispatch/emergency-services** view (hazard source on floor plan, occupancy +
unaccounted count, evacuation progress, timeline) and **Sensors** view (`/sensors`: the
hub's analysis on top, then each ESP32 with its raw status grouped like the firmware, its
own thresholds, the verbatim JSON and raw history charts, 15 min–24 h). Live over
WebSocket. On the hub it is served by nginx on port 80, same origin as the API. See
[`web/README.md`](./web/README.md).

## Mobile — Flutter resident app

`mobile/` — resident app (Flutter): emergency alerts, evacuation guidance routed away
from the hazard, and "I'm safe" check-in feeding victim-accounting. Talks to the hub
over REST + WebSocket (`--dart-define=CANARY_API=http://<pi-ip>`) and shows the sensor
analysis only ("Home status" for residents, "Building sensors" for managers), never raw
sensor values. See [`mobile/README.md`](./mobile/README.md).

## AI hazard-source triangulation

`backend/app/analytics/` — estimates the leak origin from the sensor array
(concentration-weighted centroid + time-of-first-detection, optional airflow prior),
with an honest confidence score (capped at 0.95; single-sensor degrades to zone-level).
Runs from `verification` onward for gas/CO; exposed at
`GET /api/v1/incidents/{id}/triangulation` and surfaced on the dashboard floor plan
(SOURCE marker + confidence) and the Dispatch "Hazard source (AI)" card. The estimate
can differ from the first-detection zone (it follows the concentration peak).

## False-alarm reduction

`backend/app/analytics/false_alarm.py` — classifies a sensor's recent reading window
(spike-and-decay, oscillatory cooking, sensor drift, sustained-genuine, sub-threshold
micro-leak trend) and may **hold a corroborated-by-count, non-critical signal in
`verification`** instead of alarming — e.g. a lone sensor sitting flat just over
threshold. Real cross-sensor corroboration (a second device/zone) or a clearly rising
trend escalates as genuine. **Critical readings and edge alarms are never suppressed.**
Slow sub-threshold rises open a low-severity **advisory** incident (managers only).
Assessment shown on the dashboard (signal badge); rule-based now, same features feed
an ML upgrade later (ARCHITECTURE.md §B.3).

## Known limitations

- Not yet validated on a physical Raspberry Pi with the real sensors: tests and the
  firmware-accurate simulator only.
- Username-only dashboard/app login and plaintext MQTT/HTTP: trusted LAN/VLAN only
  (RUNME §1.10).
- The demo building `bld_007` (zones, demo devices, users) is always seeded, and new
  sensors land in its `zone_hallway` until moved (`PATCH /api/v1/nodes/{id}`).
- One open incident per hazard type per building.
- The hub sends no commands to the devices yet (the firmware's valve/buzzer topics exist).
- No schema migrations: a Postgres database created by an earlier version needs one
  manual change (RUNME §1.9).

## Not yet built (see ARCHITECTURE.md roadmap §F)

TLS for MQTT/HTTP and real user authentication, real FCM/APNs delivery (wired but off
by default; needs Firebase config), hub → device commands, LoRa gateway tier,
tamper-evident audit hash-chaining, alembic migrations, external dispatch adapters. The
backend notification layer is a stub (persists + WebSocket broadcast); transports plug
in behind it. Occupancy/victim-accounting is basic (rule-based) — the ML upgrade paths
are described in ARCHITECTURE.md §B. What was built versus the plan: the "As built"
section at the top of [`ARCHITECTURE.md`](./ARCHITECTURE.md).

> ⚠️ MVP detection thresholds are illustrative engineering defaults, **not** certified
> life-safety setpoints. Canary is an advisory system in this slice — not a substitute
> for certified gas/CO alarms.
